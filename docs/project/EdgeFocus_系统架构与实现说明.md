# EdgeFocus 系统架构与实现说明

## 1. 总体架构

EdgeFocus 采用“嵌入式主机为核心、Android App 为辅助控制台、视觉与手机状态共同输入、多通道输出”的架构。

整体链路可以概括为：

```text
用户学习场景
  -> 摄像头采集桌面行为
  -> 板端视觉模块生成视觉状态
  -> Android App 上报手机使用状态
  -> 板端行为引擎融合视觉与手机上下文
  -> 提醒策略生成分级干预命令
  -> 屏幕 / 声音 / 手机 / 外设输出提醒
  -> 会话结束后生成报告
  -> App 展示历史和统计
```

系统中最重要的原则是：板端主机维护 EdgeFocus 会话的权威状态。App 可以启动、查看、同步和上报信息，但不在 EdgeFocus 模式下单方面决定会话报告。

## 2. 板端主机结构

板端项目位于 `BoardCode/focus_app`，核心语言为 C++。代码按模块拆分，方便硬件适配和团队开发。

### 2.1 app 模块

职责：

- 管理系统生命周期。
- 维护当前会话状态。
- 处理开始、暂停、继续、结束等会话控制。
- 提供全局状态快照。

典型组件：

- `SessionController`：负责会话启动、结束、预检和报告生成。
- `SystemStateStore`：集中保存系统状态、行为上下文、偏好设置和会话信息。
- 模块生命周期接口：用于统一启动、停止和调度各功能模块。

### 2.2 behavior 模块

职责：

- 接收视觉状态和手机状态。
- 进行事件检测、状态机转换和风险评分。
- 输出当前专注行为状态。

典型组件：

- `EventDetector`：把原始视觉和手机输入转换为行为事件。
- `FocusStateMachine`：决定当前候选专注状态。
- `RiskScorer`：综合持续时间、视觉状态、手机状态等因素形成风险分数。
- `BehaviorEngine`：组织行为处理流程，并把结果写入系统状态。

行为层需要明确区分三个概念：

- 手机侧上报的使用状态，例如学习、普通使用、娱乐等。
- 融合后的走神程度，这是板端综合判断结果。
- 提醒等级，这是策略层根据当前风险和规则生成的输出等级。

这三个概念不能混用，否则会导致学习类 App、娱乐类 App 和视觉走神之间的关系被误判。

### 2.3 policy 模块

职责：

- 根据当前行为状态和风险程度决定是否提醒。
- 控制提醒频率，避免频繁打扰。
- 生成具体的干预命令。

典型组件：

- `ReminderPolicy`：提醒策略核心。
- `InterventionCommand`：提醒命令数据结构。

策略层不直接读取摄像头或 App 原始信息，而是使用行为层输出的状态和风险判断。这样可以保持职责清晰。

### 2.4 network 模块

职责：

- 提供 BLE GATT 服务。
- 解析 App 命令。
- 返回 JSON 响应。
- 主动推送状态和事件。

典型组件：

- `BleGattServer`：BLE 服务与收发。
- `AppCommandService`：处理 App 命令。
- `PhoneSyncParser`：解析手机使用状态上报。

主要命令包括：

- `get_current_state`：获取当前主机状态。
- `session_control`：开始、暂停、继续、结束、跳过预检等。
- `phone_sync`：App 上报手机前台状态。
- `get_last_report`：获取最近一次会话报告。
- `get_session_history`：获取历史记录。
- `upload_local_session`：上传 App 本地会话，按 session_id 幂等保存。
- `gimbal_control`：云台控制，长动作采用即时 ACK 加后台结果推送。

### 2.5 ui 模块

职责：

- 绘制板载屏幕界面。
- 展示主页、预检、会话运行、设置、报告等页面。
- 响应按键、旋钮或触控输入。

板载 UI 需要适配小屏幕，因此布局重点是：

- 信息密度适中。
- 避免文字遮挡。
- 关键操作按钮足够明显。
- 状态、电量和连接信息不要挤压主要内容。

### 2.6 device 模块

职责：

- 抽象屏幕、声音、手环、云台、电源等硬件。
- 屏蔽不同硬件版本的驱动差异。
- 为业务层提供稳定接口。

当前项目已经开始拆分自研版硬件和正点原子硬件两个适配方向，后续应该尽量让硬件差异停留在 device 层和少量配置层，不扩散到行为和协议逻辑中。

### 2.7 storage 模块

职责：

- 保存会话历史。
- 保存设置。
- 支持报告查询和幂等写入。

板端存储让设备可以脱离手机保存基本学习记录，也能在 App 重新连接后同步历史。

### 2.8 vision 模块

职责：

- 加载视觉模型。
- 对摄像头画面进行推理。
- 将模型输出转换为行为层可以理解的视觉状态。

模型文件位于 `models` 目录，项目中包含 ONNX 和硬件部署相关模型文件，便于不同硬件环境调试。

## 3. Android App 结构

Android 项目位于 `EdgeFocusApp`，采用 Kotlin、Jetpack Compose、Hilt、Room 和 BLE 相关能力。

### 3.1 data 层

职责：

- 本地数据库。
- BLE 连接与协议。
- JSON 解析。
- Repository。

关键内容：

- Room 数据库保存会话、设置和 App 使用记录。
- BLE 管理器负责扫描 EdgeFocus 设备、连接、发送命令和接收推送。
- 协议解析器负责把主机 JSON 转换为 App 内部状态。
- 数据库迁移避免升级时清空用户数据。

### 3.2 domain 层

职责：

- 存放业务模型和用例。
- 连接数据层与 UI 层。

例如会话数据、设置数据、使用记录等都可以在 domain 层形成更稳定的业务结构。

### 3.3 presentation 层

职责：

- Compose UI。
- ViewModel。
- 页面导航。

主要页面：

- 首页：显示计时、当前模式、开始/暂停/停止。
- BLE 连接页：扫描并连接 EdgeFocus 主机。
- 控制面板：显示主机状态、控制板端功能。
- 设置页：配置默认时长、模式和其他选项。
- 历史/统计页：查看专注记录。

### 3.4 service 层

职责：

- 前台服务。
- 专注期间监控手机前台 App。
- 根据权限状态决定是否上报手机使用信息。

AppMonitorService 的关键点是：只有在 BLE 已连接且当前存在活跃 EdgeFocus 会话时，才应向主机上报手机状态。没有 Usage Access 权限时，不应该把无法识别前台 App 当成用户分心。

## 4. 会话状态协议

App 与主机之间需要保持统一状态字段，典型状态包括：

- 是否 active。
- 是否 paused。
- session_id。
- session_phase。
- session_start_source。
- focus_state。
- elapsed_ms。
- remaining_ms。
- target_duration_ms。
- distraction_count。
- reminder_count。
- phone_distraction_count。
- calibration_completed。
- precheck。
- precheck_control。
- output_capability。
- camera_preview。
- behavior_context。

其中 `session_phase` 对 App 很重要，因为它决定当前应该显示预检、运行、暂停、结束还是空闲状态。

## 5. 专注启动流程

### 5.1 App 发起

1. 用户在 App 选择 EdgeFocus 模式。
2. App 检查是否已连接主机。
3. App 发送 `session_control start`。
4. 主机创建会话并进入预检或运行阶段。
5. App 根据主机状态 hydrate 页面，不自行伪造板端会话。

### 5.2 主机发起

1. 用户在板端启动专注。
2. 主机创建会话。
3. App 连接或收到 push 后同步已有会话。
4. App 只做状态展示和辅助控制，不重复 start。

### 5.3 预检跳过权限

预检有 owner 概念。App 只有在预检 owner 允许时才能跳过。主机本地启动的预检不应该被 App 随意跳过，这能避免远端误操作破坏板端流程。

## 6. 行为融合逻辑

行为融合的目标不是把某个字段直接映射成最终提醒，而是根据多种输入形成更稳定的判断。

推荐理解方式：

```text
视觉状态 + 手机使用状态 + 持续时间 + 置信度
  -> 行为事件
  -> 当前专注状态
  -> 风险分数
  -> 提醒策略
  -> 提醒等级和输出通道
```

### 学习类手机使用

学习类 App 表示手机正在参与学习，不应直接被视为手机分心源。但它仍然是上下文，不能屏蔽视觉行为。

例如：

- 学习类 App + 视觉正常：通常不提醒。
- 学习类 App + 看向别处：可以根据视觉侧触发提醒。
- 学习类 App + 犯困或离开：可以根据视觉侧触发更明显提醒。

### 娱乐类手机使用

娱乐、游戏、视频等状态本身就有较强分心风险。即使视觉暂时正常，也可以提高风险；如果视觉也异常，则提醒等级可以更高。

## 7. 数据闭环

会话结束后，主机生成报告，字段包括：

- session_id。
- start_time_ms。
- end_time_ms。
- total_duration。
- focus_duration。
- distraction_count。
- reminder_count。
- phone_distraction_count。
- end_reason。

App 保存报告时应使用主机提供的 focus_duration，而不是简单把 elapsed_ms 当成有效专注时长。这样可以避免统计口径错误。

## 8. 电源与工作模式

系统可以根据供电状态进入不同 power_profile：

- HOME：外部供电或充电状态，工作频率较高。
- GO：电池状态，降低工作频率以省电。

这与 notification_mode 不同。power_profile 表达设备供电与功耗策略，notification_mode 表达提醒方式是否静音，两者不能混用。

## 9. 硬件版本部署

项目当前准备进入分硬件版本部署阶段：

- 自研版硬件目录用于适配团队自研 PCB、传感器、电源和外设。
- 正点原子硬件目录用于适配开发板和现有模块。

建议保持：

- 共用业务逻辑尽量不分叉。
- 硬件驱动和引脚配置放在硬件适配层。
- UI、协议、行为策略尽量保持一致。
- 每个硬件版本保留独立 README，说明差异和部署步骤。

## 10. 可展示的工程质量点

评审可重点关注：

- BLE 协议不是临时字符串，而是有命令、响应和 push 语义。
- 大包响应有分片处理，避免 BLE MTU 限制造成数据丢失。
- App Release 包禁用测试入口和模拟连接。
- Room 数据库使用正式迁移，避免升级破坏数据。
- 板端输入有边界校验，避免异常数据污染状态。
- Local 模式和 EdgeFocus 模式有不同保存策略。
- 主机和 App 都有测试覆盖关键业务逻辑。

## 11. 架构总结

EdgeFocus 的架构重点是清晰分层：

- App 负责移动端交互、手机状态输入和报告展示。
- 主机负责会话权威状态、行为融合、提醒和报告。
- 视觉模块负责把画面转换为行为信号。
- 协议层负责可靠通信。
- 策略层负责把风险转换为合适提醒。
- 硬件适配层负责屏蔽不同板卡差异。

这种结构既适合比赛答辩，也适合后续继续开发。
