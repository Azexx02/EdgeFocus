# EdgeFocus 预检确认事务可靠性设计

日期：2026-07-17

## 背景

实机偶发出现“确认并开始”按钮可点击，但点击后仍停留在预检页，无法进入正式专注会话。当前 APP 把跳过自动调整、云台微调、位置确认及进入正式会话共用同一个预检事务协调器。协调器在已有事务执行时会把后续输入直接作为成功返回，因此用户在预览、微调或状态读取尚未结束时点击“确认并开始”，确认操作可能被静默丢弃。

即使确认操作得到执行，现有流程仍会在主机接受 `skip_precheck` 后，在 10 秒内以 250 ms 间隔反复请求完整 `get_current_state`。完整状态响应包含较大的预检与设备快照，在 BLE 分片、预览图片传输或链路拥塞时，一次请求就可能耗时数秒。主机可能已经进入 `RUNNING`，但 APP 因未在超时窗口内完成额外轮询而继续显示预检页或报告超时。

2026-07-17 实机日志进一步确认了一条确定失败路径：APP 连续发送序号 3、4、5 的 `precheck_confirm_position`，主机均返回 `stale_command_sequence`，因此 APP 没有继续发送 `skip_precheck`，主机保持在 `PRECHECK`。本地数据库序号只能保证相对 APP 自身递增，无法保证覆盖安装、数据恢复或其他控制入口曾使用更大序号后仍高于主机水位。

## 目标

1. 用户点击一次“确认并开始”后，确认事务不得被其他预检命令静默吞掉。
2. 主机同步返回已进入正式会话时，APP 必须立即采用该响应，不再等待额外的完整状态轮询。
3. BLE 响应丢失或超时时，APP 必须通过一次权威状态对账判断主机实际阶段，避免主机已经运行而 APP 仍停留在预检页。
4. 确认期间禁止重复确认、云台微调和预览刷新，并提供明确的处理中状态。
5. 主机确实拒绝或仍处于 `PRECHECK` 时，APP 恢复可操作状态并显示可理解的错误，允许用户重试。
6. 本次只修改 APP，不要求重新部署主机。
7. 云台命令序号必须在 APP 重启、覆盖安装、本地检查点缺失或主机保留同一预检会话时仍能立即高于旧水位，不能依靠用户反复点击逐个追赶。

## 方案选择

采用“高优先级确认事务 + 响应驱动状态收敛 + 单次权威对账”的方案。

不采用单纯延长 10 秒超时，因为它无法解决确认点击被静默丢弃，并会继续用密集的大响应轮询占用 BLE。也不采用仅提示“操作繁忙、请重试”，因为现场展示需要一次点击可靠完成，不能把竞争条件交给用户处理。

## 事务模型

预检交互分为普通事务和终止事务：

- 普通事务：跳过自动调整、云台方向微调、回中、停止、重新对准。
- 终止事务：确认位置并进入正式会话。

普通事务继续串行执行，重复快速点击可以拒绝或丢弃，但必须向调用层返回明确的 `Busy` 结果，不能伪装为成功。终止事务具有最高用户意图优先级：点击后立即进入 `Confirming` 状态，停止新的预览请求和普通事务入口；若已有普通事务正在执行，则等待其自然完成后执行确认，不将确认操作丢弃。重复点击确认以及首页、横向控制面板同时发起的确认必须复用同一个进行中结果，不重复发送主机命令。

`Confirming` 状态、当前确认任务及预检独占协调器归属于 `@Singleton PrecheckController`，由该控制器通过 `StateFlow` 暴露给两个 ViewModel。ViewModel 只负责观察和触发，不拥有确认任务。页面切换、ViewModel 清理或 Activity 重建不得取消已经提交的确认；只有连接丢失且无法对账、会话身份变化、应用进程终止或事务正常完成才结束该任务。

等待已有事务必须受 BLE 命令自身超时边界约束，不能无限阻塞。若已有事务失败，确认事务仍应在重新校验当前会话阶段、会话 ID、准备状态以及云台手动租约/状态后决定是否继续；不能沿用点击时的旧 UI 快照。只有连接不可用且无法对账、会话已变化或主机不再处于 `PRECHECK` 且也未进入 `RUNNING` 时才终止。

## 确认命令流程

1. 用户点击“确认并开始”。单例 `PrecheckController` 原子地建立或复用当前确认任务，设置 `isPrecheckConfirming = true`，清除上一次预检错误。
2. APP 停止新的预览循环并取消待排队的相机预览请求，UI 禁用确认、跳过、微调、回中、重新对准和手动刷新预览。已经在 BLE 链路中传输的预览不能被强制中断，允许它在自身超时内自然完成；确认事务必须取得它之后的下一执行权。
3. 确认事务取得预检命令独占权，校验本地仍是同一个 `session_id`、阶段为 `PRECHECK`，且准备状态为 `READY` 或 `DEGRADED`。
4. 存在云台且当前权威状态为手动租约有效时，发送一次 `precheck_confirm_position`。若不存在云台则跳过该命令。命令被明确拒绝时保留在预检页并展示主机错误。若命令传输超时或响应无法解析，必须先执行一次位置确认对账，不得盲目重发：
   - 已是同一会话的 `RUNNING`/`FOCUSING`：整个确认成功；
   - 同一会话仍为 `PRECHECK`，云台为 `holding`/`position_confirmed` 或 `manual_lease=false`：视为位置已确认，继续步骤 5；
   - 同一会话仍为 `PRECHECK` 且仍有手动租约：视为本次位置确认未完成，恢复可重试状态；
   - 对账失败、会话变化或状态不明确：不重发位置确认，恢复 UI 并提示连接/状态错误。
5. 发送一次带当前 `session_id` 的 `session_control(action = "skip_precheck")`。
6. 解析这次 `session_control` 响应自身携带的 `runtime_snapshot.session.phase`，兼容旧字段 `session_phase`：
   - 阶段为 `RUNNING`/`FOCUSING`：立即把该响应应用到 `TimerStateHolder`，结束确认事务并进入正式会话。
   - 阶段仍为 `PRECHECK` 或阶段缺失：进入一次状态对账。
   - 响应明确拒绝：不做盲目重发，恢复预检操作并显示拒绝原因。
7. 如果 `session_control` 发生传输超时或响应无法解析，也进入一次状态对账，因为命令可能已经被主机执行。进入对账前以及对账请求失败后，先检查 `TimerStateHolder` 是否已通过权威 push 收到同一会话的 `RUNNING`/`FOCUSING`；若是则直接成功。

## 云台命令序号

主机仅要求同一预检会话中的云台命令序号严格递增，不要求连续。APP 分配序号时使用 `max(本地检查点, 主机已公开水位, 当前 Unix 毫秒时间) + 1`，而不再从 1 开始逐次追赶。Unix 毫秒基线可使覆盖安装或本地记录缺失后的首条命令立即超过过去的小整数水位；本地检查点仍保证系统时间回拨时进程内与数据库内不倒退。所有云台预检命令共用该分配规则。

若主机仍明确返回 `stale_command_sequence`，APP 将其作为可诊断错误展示并记录命令、session ID 与已分配序号；本次不自动无限重发。下一次用户操作会基于新的时间/检查点获得更大序号。

## 单次权威状态对账

每个不确定命令阶段最多请求一次 `get_current_state`，不再在 250 ms 循环中连续请求完整状态。位置确认与 `skip_precheck` 是两个不同的副作用边界：前者的不确定响应完成一次位置状态对账后，若能够确定位置已确认，仍可继续发送 `skip_precheck`；后者再发生不确定响应时可进行一次会话阶段对账。对账结果按以下规则处理：

- 同一 `session_id` 且阶段为 `RUNNING`/`FOCUSING`：确认成功，应用状态并进入正式会话。
- 同一 `session_id` 且阶段仍为 `PRECHECK`：确认未完成，恢复按钮并提示“主机仍在预检，请重试”。
- 阶段为 `IDLE`：提示会话已结束或被主机取消，并交给现有状态同步恢复首页。
- `session_id` 已变化：不覆盖新会话，提示会话状态已变化。
- 对账也失败：恢复操作，显示连接/超时错误；现有连接监督器继续负责重连，重连后的常规状态同步仍可把主机的 `RUNNING` 或 `PRECHECK` 状态接管回来。

对账期间保持 `isPrecheckConfirming = true`。完成任何终态处理后必须在 `finally` 中清除此状态，避免异常路径永久禁用按钮。

## 状态应用与 UI

`TimerStateHolder` 提供可复用的“应用主机命令响应”入口，与现有 `refreshBoardState()` 使用相同解析和会话接管规则，避免 ViewModel 私自构造运行状态。该入口只接受通过业务成功校验、且会话身份连续的权威响应。

同一 `session_id` 的阶段必须保持单调：一旦已应用 `FOCUSING`/`RUNNING`，并发队列中更早发起但更晚到达的 `PRECHECK` 响应、轮询或 push 不得把 APP 状态回退到预检页。实现使用确认事务 epoch 或同会话阶段不可逆规则过滤陈旧观察；新 `session_id` 不受旧会话规则影响。

首页预检页和横向控制面板预检页共同读取单例控制器暴露的 `isPrecheckConfirming`：

- 确认按钮显示“正在进入专注…”并禁用；
- 所有可能产生 BLE 预检命令的控件同时禁用；
- 页面保持预检布局，不新增弹窗或改变既有 UI 风格；
- 成功后由统一 `TimerStateHolder` 状态切换进入原有正式会话页面；
- 失败后在现有错误信息区域显示原因，并恢复“确认并开始”。

## 错误与幂等策略

- 忙碌不再返回假成功。普通事务被繁忙策略拒绝时返回明确错误；确认事务则等待独占权。
- 同一次 UI 确认只发送一次 `precheck_confirm_position` 和一次 `skip_precheck`，不因状态确认超时自动重发可能产生副作用的命令。
- 对账发现主机已运行时视为成功，即使原始命令响应超时。
- 主机返回会话不匹配、预检阶段已变化或位置确认失败时，原样保留有用错误并补充中文提示。
- 页面销毁或 ViewModel 清理只停止观察，不取消单例控制器中已提交的确认。确认任务自身的成功、失败或取消路径必须在 `finally` 中释放事务独占权和 `isPrecheckConfirming`，不得留下进程级死锁。

## 测试与验收

### 单元测试

1. 普通云台事务执行中发起确认，确认等待后恰好执行一次，不被当作成功丢弃。
2. 两次快速确认以及首页、横向控制面板同时确认会复用同一个结果，不重复发送位置确认或 `skip_precheck`。
3. `session_control` 响应直接包含 `RUNNING` 时，不调用 `get_current_state`，立即应用状态。
4. `precheck_confirm_position` 已执行但响应丢失，对账得到同一会话 `PRECHECK + holding/manual_lease=false` 时不重发位置确认，继续发送一次 `skip_precheck`。
5. 位置确认真正未执行且对账仍有手动租约时，恢复可重试状态，不发送 `skip_precheck`。
6. `skip_precheck` 响应超时但共享权威 push 或单次对账返回同一会话 `RUNNING` 时，结果为成功。
7. 响应仍为 `PRECHECK` 时每个命令阶段最多对账一次，恢复 UI 并返回可重试错误。
8. 主机明确拒绝时不重发命令、不进入 RUNNING。
9. 旧 PRECHECK 响应晚于 RUNNING 响应到达时，同一会话不得回退。
10. `realign` 或微调结束后租约发生变化时，确认取得独占权后按最新权威状态处理。
11. 会话 ID 变化、阶段变为 IDLE、连接失败和确认任务取消均释放确认状态与事务锁；ViewModel 清理和页面切换不取消确认。
12. 无云台以及仅返回 `success + session_phase` 的旧协议响应可以正常进入会话。
13. 状态缺失、非法 session ID 和无法解析响应均不构造虚假 RUNNING。
14. 首页和控制面板在确认期间禁用全部预检命令入口，成功/失败后状态正确恢复。
15. 本地检查点为 2、主机水位高于 5、当前 Unix 毫秒为大值时，首次分配即使用时间基线以上的序号；系统时间回拨时仍高于本地检查点。

### 实机验收

使用无线 ADB 设备 `192.168.10.59:33941`，覆盖安装新 APK 后至少执行以下场景：

1. 自动调整结束后直接点击一次确认，进入正式会话。
2. 点击一次方向微调后立即确认，确认不丢失并进入正式会话。
3. 相机预览正在刷新时确认，预览请求让路，进入正式会话。
4. 快速连续点击确认，不产生重复会话或重复主机命令。
5. 点击确认后立即切换首页/横向控制面板或触发 Activity 重建，确认事务继续完成且不重复发命令。
6. 连续完成至少十轮“开始预检 → 确认 → 正式会话 → 结束”，不得出现仍停留预检页的偶发失败。
7. 在确认阶段至少一次人为制造 BLE 延迟、断包或断连，重连后 APP 必须同步到主机实际的 `RUNNING` 或 `PRECHECK`，不能卡在不可操作状态。
8. 保持主机处于同一 PRECHECK 会话并覆盖安装 APP，首次点击确认不得再收到 `stale_command_sequence`，且主机随后进入正式会话。

日志验收需能区分：确认已排队、位置确认响应、`skip_precheck` 响应阶段、是否执行单次对账、最终收敛阶段和失败原因。

## 非目标

本次不修改主机预检、云台搜索、微调角度、识别推理或会话计时逻辑；不改变预检页面布局和视觉风格；不增加新的用户配置；不通过反复重发命令掩盖连接问题。
