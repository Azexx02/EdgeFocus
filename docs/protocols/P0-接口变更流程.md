# P0 接口变更流程

> 日期：2026-06-29  
> 适用范围：主机、App、手环之间的所有跨端接口

---

## 1. 哪些改动必须走本流程

以下任一变更都必须先改文档、再改代码：

- BLE Service UUID、Characteristic UUID、设备广播名、角色方向。
- App ↔ 主机 JSON 命令名、请求字段、响应字段、push 事件字段。
- 主机 ↔ 手环二进制帧类型、字段含义、特征读写方向。
- FocusState、CommandLevel、系统模式、反馈枚举等跨端枚举。
- 会话报告、统计、历史记录、偏好设置字段。
- MTU、分片、分页、Notify 行为。
- 手环是否新增 ACK、Notify、电量上报、状态读取等上行能力。

---

## 2. 变更流程

1. 提出变更原因：说明为什么现有冻结接口无法满足需求。
2. 修改对应文档：
   - App ↔ 主机：`doc/03-主机手机协议.md`、必要时 `doc/04-手机App文档.md`、`doc/08-主机Todo.md`。
   - 主机 ↔ 手环：`doc/02-主机手环协议.md`、必要时 `doc/05-手环文档.md`、`doc/06-手环Todo.md`。
   - 总体流程：`doc/01-主体文档.md`、`项目推进计划.md`。
3. 更新 `P0-协议冻结清单.md`：标明新增、修改或废弃字段。
4. 三端影响评估：列出主机、App、手环分别要改哪些模块。
5. 按顺序实现：先权威端，再消费端。
6. 增加或更新测试：至少覆盖协议解析、字段回显、异常兼容。
7. 三端联调验证：用真实设备或可替代 smoke 工具验证。
8. 记录变更结果：在相关 Todo 或推进计划中标记完成。

---

## 3. 实现顺序原则

### App ↔ 主机接口

推荐顺序：

```text
主机协议处理/测试
  -> App BLE 调用/解析
  -> App UI 消费
  -> 真实 BLE 联调
```

原因：主机是数据权威，App 依赖主机响应和 push。

### 主机 ↔ 手环接口

推荐顺序：

```text
手环固件解析/执行
  -> 主机写入/诊断
  -> 主机策略触发
  -> 真实手环联调
```

原因：手环当前没有业务上行，必须先确认手环能正确消费帧。

## 4. 兼容性规则

- 普通 App 响应必须保留 `id` 回显，不能破坏已有请求匹配。
- App 历史同步在没有分片前保持小 payload，默认继续使用 `limit=1`。
- `phone_sync` 响应继续视为 ACK/调试；UI 状态以 `push_state/get_current_state` 为准。
- 手环 Alert 帧 `{0x01, pattern, level}` 不得破坏。
- 手环没有上行能力前，不得在 App 或主机 API 中承诺手环电量、ACK 或展示成功确认。
- 新字段应优先做可选字段，避免老版本 App 或主机直接失败。

---

## 6. 禁止事项

- 禁止只改代码不改冻结文档。
- 禁止 App 或手环自行解释主机权威字段。
- 禁止把手环本地能力写成主机可读取能力，除非新增了实际上行协议。
- 禁止在一个变更中同时混入协议改动、UI 改动、硬件调参而不拆分验收。
