# 现场运行稳定性热修设计

## 目标

修复新版程序在 PRECHECK 云台搜索期间出现的两类已证实故障：搜索总时长突破配置上限、Demo HTTP 状态轮询被云台同步锁拖死。保留新版视觉预览、紧凑搜索、会话内微调和强制释放功能。Wi-Fi 与蓝牙本轮不修改策略，只作为新旧版本 A/B 验收项；新版验收失败即恢复已验证可用的上一版。

## 已确认故障

- 板端日志显示 PRECHECK 从 `01:24:34` 到 `01:25:12`，总计约 38.5 秒，超过 12 秒硬截止。
- `moveToVerified`、角度查询及补偿运动均为同步调用；控制器在调用期间持有自身互斥锁，墙钟截止只能在调用返回后检查。
- Demo HTTP 使用单一普通请求处理线程，`/api/demo/state` 会同步读取云台控制状态；争用时单个请求超过 4 秒，浏览器轮询随后堆积。
- 回滚上一版二进制和配套配置后，板端本机 Demo HTTP 立即恢复 HTTP 200，BlueZ 广告为 1 且手机重新连接。该 A/B 结果说明新版控制阻塞链是当前优先修复对象，但不足以证明 Wi-Fi 掉线的底层触发因素。

## 方案

### 1. 有界 PRECHECK 搜索

- 搜索启动时生成单调绝对截止时间。搜索航点、候选冻结、候选居中/跟踪、角度查询和结束 HOLD 等全部 PRECHECK 同步硬件调用的超时均取剩余绝对预算，其中单次上限为 800 ms；不得在 PRECHECK 内进入长验证/补偿链，预算不足时不再发送新运动。
- 自动搜索航点只发送经过安全边界检查的短超时定位命令，不在 PRECHECK 搜索线程内执行长时间闭环角度验证和补偿。搜索期间的视觉观察和航点间隔仍由现有状态机推进。
- 12 秒定义为从 `PRECHECK search started` 到人工控制可用或安全降级，包含结束 HOLD。结束搜索时不再执行 8 秒闭环回中；未找到人时优先在当前位置 HOLD 并交还人工微调。
- 任一命令超时、UART 错误或 FAULT 都终止后续航点并递增控制代次。若剩余预算无法确认 HOLD，则停止接受人工运动并进入降级，而不是让旧运动与人工微调重叠。新会话/人工接管同样递增控制代次，迟到状态不得覆盖新状态。
- 手动接管最多等待当前 800 ms 短命令结束，不再被数十秒验证链阻塞。
- 人工微调、正式跟踪与安全边界仍保留原有验证规则；本热修只放宽自动搜索阶段。

### 2. HTTP 与云台锁隔离

- `/api/demo/state` 不得等待云台控制器互斥锁。控制器提供 `trySnapshot`；成功快照必须携带当前 `session_id` 和控制代次。
- 拿不到锁或会话/代次不匹配时，Demo HTTP 只使用权威会话发布器中的只读显示状态，禁用全部云台按钮并返回 `busy`，不得复用上一会话的可操作状态。
- 自动搜索内单次同步硬件调用已收敛到 800 ms；前端轮询保持最多一个在途请求，并设置超时，避免客户端排队放大。
- 验收标准：PRECHECK 运动期间板端本机连续请求 `/api/demo/state`，每次必须在 1 秒内返回；页面仍可刷新并最终开放接管按钮。

### 3. 现场恢复与回退

- 仅在 Wi-Fi 已关联且缺少 IPv4 时，对 `wlan0` 的唯一现有 `udhcpc` 实例执行一次续租；不得启动第二个 DHCP 客户端。验证目标 IPv4、默认路由和连通性。
- 新二进制与配置作为同一版本单元写入 staging；切换前验证 staging 和 previous 均完整，停服务后成对激活。
- 部署后由网页真实执行：启动会话、观察搜索、接管微调、发送一个微调动作、结束会话。
- 若服务、HTTP 1 秒响应、手机 GATT 广告、Wi-Fi/路由、PRECHECK 12 秒交权或网页控制任一项失败，停新服务、成对恢复上一版二进制和配置、重启并重新验证服务、HTTP、GATT、`wlan0` IPv4、默认路由及实际连通性。

## 测试

- 单元测试覆盖：搜索指令超时上限、剩余预算不足、结束 HOLD 失败安全降级、硬截止不被航点操作突破、非阻塞快照争用及跨会话状态拒绝。
- 主机回归：云台 PRECHECK、硬件服务、Demo HTTP、BLE GATT、会话运行时。
- 板端验收记录服务日志中的 PRECHECK 起止时间、HTTP 请求耗时、BlueZ 广告状态和 Wi-Fi IPv4 地址；完成一次新版本失败时的回滚复验路径检查。
